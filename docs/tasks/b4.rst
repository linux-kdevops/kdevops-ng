==
b4
==

Two :term:`tasks <Task>` take a series from a mailing list by its
Message-ID with `b4`_. One applies it in a worktree you add at the
series' base, and one keeps the thread there. With ``ID`` the
Message-ID the series was posted as, ``BASE`` the commit its cover
letter names as ``base-commit`` and ``BRANCH`` a name of yours for the
series:

.. code-block:: console
   :caption: host
   :class: cmd-host

   $ tasks/b4/mbox --directory ~/qemu --message-id ID --project qemu
   base_commit=BASE
   $ git -C ~/qemu worktree add -b BRANCH ~/wt/qemu BASE
   $ tasks/b4/shazam --directory ~/wt/qemu --message-id ID \
       --project qemu
   $ tasks/b4/mbox --directory ~/wt/qemu --message-id ID --project qemu
   $ tasks/qemu/series --directory ~/wt/qemu --range BASE..

b4 applies a series onto the commit the worktree has checked out and
looks for no base. ``mbox`` prints the commit the series names in its
cover letter, where it names one, so the first run, in any tree of the
project, says where to add the worktree. A tree that lacks that commit
fetches it first.

:src:`shazam <tasks/b4/shazam>` runs ``b4 shazam --add-link``, so each
commit ends with a ``Link:`` to its message. b4 reads your own
configuration, the keys it checks attestation against included. The
base is the commit you checked out, so the range of the series
(:ref:`records-series`) starts there. b4 names no branch for what it
applies: the commits land on the branch the worktree is on, which
``-b`` made here, and that branch is what you push to publish them. A
series that does not apply leaves ``git am`` stopped in the worktree,
and ``git am --abort`` there gives the base back.

:src:`mbox <tasks/b4/mbox>` runs ``b4 mbox`` and keeps the thread as
``build/logs/b4-mbox/thread.mbx`` of the worktree. The series task hands
that file to :cmd:`krecord` ``series``, which names the series by its
Message-ID and takes the cover letter from it. A thread left from
another series is not used: :cmd:`krecord` ``series`` takes it only when
its patches are the commits of the range.

Both leave a record (:doc:`/records`) under the series' Message-ID, not
under a commit of the worktree: ``b4/shazam.json`` for the series applied
and ``b4/mbox.json`` for the thread fetched, each holding what b4
printed. The thread is also kept as ``b4/mbox.mbx`` beside them, for a
reader who has no worktree. A series that does not apply has these
alone. ``--project`` names the project the worktree is of, ``linux``
or ``qemu``, which the records lie under.

The keyring
===========

b4 checks each patch's signature with `patatt`_, against the keyrings
your Git configuration lists. The red marks of a run with none mean no
key was found, and the series applies all the same. `pgpkeys`_ is the
kernel.org developers' keyring:

.. code-block:: console
   :caption: host
   :class: cmd-host

   $ git clone https://git.kernel.org/pub/scm/docs/kernel/pgpkeys.git \
       ~/.cache/b4/pgpkeys
   $ tasks/pgpkeys/verify --directory ~/.cache/b4/pgpkeys
   $ git config --global --add patatt.keyringsrc ~/.cache/b4/pgpkeys/.keyring

:src:`verify <tasks/pgpkeys/verify>` checks that the clone's commit is
signed by the key of its maintainer, Konstantin Ryabitsev. The task
names the key, and :cmd:`gpg` trusts nothing but it, in a home of its
own that goes with the task. Run it after each pull. The keyring holds
OpenPGP keys: a patch signed with a patatt ed25519 key shows no key
until a keyring of yours holds it.
